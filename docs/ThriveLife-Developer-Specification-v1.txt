Part 1: What You Are Building
1.1 Product in One Paragraph
ThriveLife is a real-time capacity-navigation app based on the book Live Recharged. It helps people notice when their energy is running low, identify which part of their life is most depleted, and take the smallest effective action to recharge — rather than adding more pressure. It is not a habit tracker, mood diary, diagnostic tool, or motivational platform. Its distinctive value is translating the book's framework into a daily personal dashboard.
1.2 Core Promise
Understand what is draining you and take the next right step to recharge.
Every feature in the app should pass this test: does it help the user notice, match, or respond? If it only measures, tracks, or educates without leading to action, it does not belong in Version 1.
1.3 The Book's Central Reframe
The manuscript's foundational idea — which must guide every screen, every result message, and every notification — is this:
What appears to be a motivation or discipline problem may actually be a capacity problem. Low power calls for a pit stop, not greater self-pressure.
This means: no shame-based language, no streak-loss penalties, no red alerts for ordinary fluctuation, no rewards for over-engagement. The app should help users leave the app and re-enter their lives with greater clarity.
1.4 Audience
Version 1 targets adults: parents, caregivers, professionals, business owners, helping professionals, leaders, and people experiencing ordinary overload, depletion, or burnout risk. Future versions may add faith-based content, teen accounts, workplace teams, and coaching pathways — none of those belong in this build.
1.5 What This Document Covers
This is a standalone specification. It incorporates and critically revises the original product outline (the App Plan), resolving architectural gaps, scoring logic, safety requirements, and build sequencing. Where this document conflicts with any earlier plan, this document is current. Section 12 lists every conflict and the reasoning.
CRITICAL: Every numeric threshold in this document is provisional expert judgment — not validated against real user data. All thresholds must be stored in an admin-editable configuration table, never hard-coded, so they can be recalibrated after pilot testing without a code release.

Part 2: The Conceptual Model
You do not need to read the book to build this app. You do need to understand these seven concepts, because they are the domain language the entire data model uses.
2.1 DRAIN
DRAIN is the state that develops when life's demands exceed current capacity. The pattern includes demands running high, avoidance, and ineffective numbing. The book presents DRAIN as a dashboard warning light, not a character failure. Relief may briefly reduce pressure, but recharge restores usable capacity. The word DRAIN appears throughout the app as a recognizable signal.
2.2 Seven Life Batteries
The book organizes human capacity into seven systems called Life Batteries. These are the core domain objects of the entire app.

2.4 Dashboard Signals
Signals appear through body, brain, and behavior. The user's job is to read the signal without turning it into a judgment about character. The app should mirror this — display information, not verdicts.

2.7 Plan A and Plan B
Every selected recharge has two versions. Plan A is the normal-day version. The app must never treat Plan B as a lesser outcome.

3.3 Construct Registry — The Key Architectural Decision
The DRAIN Check items measure the same underlying constructs as the Full Assessment's Strain items, just at a different timeframe (right now versus past two weeks). If these are developed independently, they will diverge in wording and produce contradictory readings.
Required model: every item belongs to a construct. A construct may have multiple timeframe variants. When Joel edits a construct definition in the admin panel, both timeframe variants surface together.

3.4 Response Scales — Do Not Normalize
The four instruments use three different response formats measuring different timeframes. These are deliberately not normalized to a common numeric scale. Normalizing them invites the code to average across them, which is the failure this section exists to prevent.
'Unsure' and 'Not applicable' are never scored as a middle value. Store as null, count separately. A Battery Scan answer of 'Unsure' prompts one disambiguating follow-up ('Would you say it's closer to Low or Steady?') and is otherwise treated as missing.
3.5 Conflict Display Rule
When today's Battery Scan disagrees with the standing Full Assessment state, display both. Never merge them.
The battery ring shows the Full Assessment state (the two-week pattern). A marker on the ring shows today's Scan reading. Where they diverge by more than one level, the interface names it: "Your Physical battery usually reads Steady. Today you marked it Low."
That divergence is meaningful information for the user. Reconciling it into a single averaged number destroys it.

Part 4: Scoring Logic
4.1 Three Scores Per Battery — Never Combined
Each battery produces three independent scores from the Full Assessment. These are reported separately and never averaged into a single battery number.

Score
Computed As
Direction
Capacity
Mean of completed Capacity items (3 items)
Higher = more capacity
Strain
Mean of completed Strain items (3 items)
Higher = more strain
Recharge
Mean of completed Recharge items (2 items)
Higher = more skill
No reverse-scoring. Strain items are scored in their own direction and reported as strain. Every item is worded so that a higher number means more of the thing the item names. No negatively-worded items within any scale.
4.2 Missing Data Rules
A dimension score (Capacity, Strain, or Recharge) is computed if at least 2 of 3 items are answered (or 2 of 2 for Recharge). Below that minimum, the dimension is stored as 'insufficient_data' — not zero, not imputed.
A battery state is computed only when all three dimension scores are available.
A full dashboard is computed if at least 5 of 7 batteries have states. Below that, show partial results and name which batteries are incomplete.
N/A responses count as missing for scoring and are tracked separately for pilot analysis. Any item drawing over 15% N/A in the pilot is a candidate for rewriting.

Part 5: The Overcharge Effect
5.1 Why Overcharge Is a Flag, Not a State
Overcharge is a relationship between batteries — one area (usually Work and Daily Purpose) is being sustained by drawing energy from others. It cannot be derived from a single battery's own three scores, so it cannot belong in the state enum alongside Low, Steady, and Well Charged. If you put it in the same enum, the state machine literally cannot produce it from its own inputs.
Model it as a boolean flag with a contributing-battery list, computed after all seven states are resolved.
5.2 Provisional Detection Rule
Set overcharge_flag = true when ALL of the following hold:

Condition
Rule
Why It Matters
1
Work & Daily Purpose Capacity ≥ 3.0
Output is strong
2
At least 2 of {Physical, Relational, Spiritual, Daily Rhythms} have Capacity < 2.0
Other batteries are depleted
3
Mean Strain across all 7 batteries ≥ 2.0
System-wide strain is present
4
At least one Work strain item about difficulty stopping scores ≥ 3
Cannot disengage from the overcharged area
Condition 4 is what separates overcharge from healthy high engagement. Someone with strong work capacity, low strain, and no difficulty stopping is doing well — telling them otherwise is wrong. This condition is the one most in need of pilot validation.
5.3 Message Constraints
Approved pattern: "Your results may suggest that one area is being sustained by drawing heavily from other batteries."
Never use: burnout, at risk, unhealthy, warning, workaholic, or any second-person character attribution.
The flag never appears as a red alert. It appears as an observation with a reflection prompt and a recommended starting battery from the depleted set. The user can dismiss it; dismissal is stored and the flag is not re-raised until the next Full Assessment.

Part 6: Driving Mode
6.1 User-Declared, Not Computed
Driving Mode is set by the user through the Weekly Mode Check. It is not derived from assessment scores. The self-report takes seconds and reflects today's actual road. A value derived from a two-week-old assessment will contradict what the user knows to be true, and the manuscript presents mode as something the driver reads, not something the car computes.
6.2 Advisory Suggested Mode
The system computes a suggested mode and offers it as a default the user can accept or override. It never sets the field silently.
Signal-count rule: a battery is 'showing a signal' when at least 2 of its 3 Strain items score ≥ 3 (Often or Almost always).

7.3 Re-administration of the Full Assessment
User-initiated, inside an interval structure:
Hard floor: 14 days since the last Full Assessment. The instrument's recall window is two weeks; shorter intervals produce overlapping, non-independent measurements.
Blocking copy: "Your last full assessment was [N] days ago — it looks back over two weeks, so give it a little more time. Your daily check-ins are tracking in the meantime."
Prompted at Tune-Up review points (30 / 60 / 90 days) and at 90 days for anyone who has not retaken. Store interval_days with every result. Two results fewer than 14 days apart are never rendered as a trend.
7.4 Displaying Change Over Time
Full Assessment results: discrete snapshots (baseline versus current), not a continuous line.
Daily Check-In data: continuous line, on a separate chart.
Never merge these two data sources on one axis.
CRITICAL: Until pilot data establishes a standard error of measurement, show direction and state labels, never numeric deltas. "Your Physical battery has moved from Low to Steady" is supportable. "+0.7" is not, because nothing yet tells you whether 0.7 is real movement or noise.
Assessment version is stored with every result. Results from different item versions are never compared numerically.
7.5 Restart Rail
When a user misses a planned recharge, the app does not announce a lost streak. Instead:
Message: "Nothing is lost. Practice the return."
Buttons: Do 2 minutes now / Use Plan B / Schedule my next return.
Track: time between miss and return, number of successful returns, Plan B usage, four-out-of-seven consistency. Do not track: shame-based streak loss, failed-day counts, or rankings against other users.
7.6 One Battery Tune-Up
Longer-term growth focused on one battery for 30, 60, or 90 days. Requires a completed Full Assessment.

Step
Action
1
Identify the recurring warning light
2
Select the battery that would reduce the most friction if supported
3
Choose one daily action that works on a hard day
4
Choose one support action (prepare environment, tell a trusted person, use a visible cue, reduce friction, schedule rest, move phone, prepare food/water, block time)
5
Select interval: 30 / 60 / 90 days
6
Define the win: what would become a little easier?
At the end of the interval, the review asks: What became easier? Which warning light decreased? What friction remained? Was Plan B small enough? Which support action helped? Should the user continue, deepen, simplify, switch battery, or enter maintenance mode?

Part 9: Safety, Escalation, and Privacy
CRITICAL: This section requires review by Joel in his registered capacity and legal review before beta. Do not ship without sign-off.
9.1 What the App Is Not
ThriveLife is a wellness and self-reflection tool. It does not provide diagnosis, treatment, or emergency support. This statement must be visible during onboarding and accessible from the help menu at all times.
9.2 No Risk-Screening Items
The assessment contains no items about self-harm, suicidality, substance dependence, or abuse. This is deliberate. Screening for risk creates a duty to respond to it, and an app without a monitored clinical pathway cannot discharge that duty. The correct posture is a wellness tool with an always-available support pathway, not a screener with an unstaffed alarm. Document this rationale.
9.3 Always-Available Support Layer
A persistent, non-alarming support link in the help menu and at the foot of every results screen, listing regional crisis and mental health resources. Available regardless of any score. Never triggered by a score. Never conditional. Never framed as a response to what the user answered.
9.4 Tier 1 — Sustained Low Pattern
Condition: 4 or more batteries at state Low across two consecutive Full Assessments at least 14 days apart.
Response: a non-alarming card on the results screen:
"Several areas have been reading low for a while now. ThriveLife is built for ordinary depletion, and some things need more support than an app can offer. Talking with a doctor or a counselor is a reasonable next step, and it is not a sign that anything has gone wrong."
Includes a 'find support' link and a dismiss control. Does not block the app. Does not repeat within 30 days.
9.5 Tier 2 — Physical Symptom Persistence
Condition: Physical Capacity < 1.5 sustained across two assessments.
Response: the book's own guidance about persistent physical symptoms warranting medical attention, in the book's voice.
9.6 Free-Text Fields
The optional journal and 'what drained you today' field: no automated classification. Do not run NLP, sentiment analysis, or keyword detection on free text to identify risk. The always-available support layer is the response. Building a detector that is wrong in either direction is worse than not building one.
9.7 Age Gate
Self-declared 18+ at signup. Teen accounts are deferred to a future version and must remain so — a minor-facing wellness assessment carries consent and duty considerations this architecture does not address.
9.8 AI Rules
AI features should be added after the rule-based system works. When added, AI may: rewrite recommendations in the user's preferred tone, summarize weekly patterns, offer reflection questions, suggest Plan B alternatives, help choose between recharge options, convert a journal entry into a brief reflection, suggest a steering sentence, and help simplify an oversized plan.
AI must not: diagnose, claim to detect trauma or mental illness, assess crisis risk, make medical recommendations, decide who accesses user data, pressure users to disclose, infer hidden emotional states, or replace the rule-based scoring model.
9.9 Privacy Requirements
Private by default. Assessment answers, scores, battery status, driving mode, journal entries, recharge completion, support needs, AI conversations, and tune-up progress remain private unless the user actively shares them.
Required user controls: export data, delete data, delete account, disable notifications, disable AI features, control journal retention, choose whether anonymous usage data is collected, choose what may be shared with a future team.
DEV NOTE: Alberta PIPA and PIPEDA apply to repeated wellness data. Privacy review is required before beta. The handling model for stored assessment responses — retention period, encryption at rest, cross-border storage — must be specified by legal counsel.

Part 11: Build Phases
11.1 Phase 1 — Content Architecture (Joel's responsibility)
Before development begins, Joel delivers: final terminology dictionary, chapter-to-app content map, seven battery construct definitions, candidate item bank with construct IDs, recharge action library, result interpretation copy, safety copy, and notification copy. The developer should not begin scoring or recommendation logic without this content.
11.2 Phase 2 — Core Data Model and Admin
Build the database schema (Section 10), the admin content editor, and the scoring_thresholds config table. Verify that Joel can create, edit, and version assessment items, constructs, recharge actions, result wording, and scoring thresholds without code changes. This is the foundation everything else depends on.
11.3 Phase 3 — Assessment Engine
Build all four instruments: DRAIN Check, Battery Scan, Full Assessment, Weekly Mode Check. Implement the scoring logic from Section 4, the battery state matrix, the overcharge flag from Section 5, and the driving mode system from Section 6. Verify that each instrument writes only to its authorized dashboard elements (Section 3.2).
11.4 Phase 4 — Dashboard and Recommendations
Build the dashboard with the five elements from Section 8, the recommendation engine as a rule-based lookup table (not hardcoded conditionals), Plan A/Plan B system, and the conflict display rule from Section 3.5.
11.5 Phase 5 — Daily Loop
Build the Daily Check-In, Restart Rail, and progress tracking. Implement the two-chart separation (Full Assessment snapshots versus Daily Check-In continuous line). Build the Tune-Up setup and review flows.
11.6 Phase 6 — Onboarding
Build the onboarding sequence from Section 7.1. This comes after the core engine works, not before — you need a working Battery Scan, Pit Stop, and Full Assessment before the onboarding flow can connect to them.
11.7 Phase 7 — Safety and Privacy
Implement the always-available support layer, escalation tiers, age gate, data export, data deletion, and privacy controls. This must be complete before any beta user sees the product.
11.8 Phase 8 — Pilot Instrumentation
Before beta launch, add telemetry: per-item response timestamp, per-screen dwell time, abandonment point, N/A and skip flags, device type, assessment version, interval since previous administration. This data drives every threshold recalibration in this document.
DEV NOTE: Phases 2-5 can overlap. Phase 7 (safety) must be complete before beta. Phase 8 (telemetry) must be complete before beta. Phase 6 (onboarding) can be a simple linear flow initially and refined after user testing.
